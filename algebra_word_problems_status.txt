1. WHAT THIS IS
---------------
The calculator project (Python, GUI in main.py, Rust port in rust_calculator/) is getting an ALGEBRA WORD PROBLEM feature: text pasted in the Templates text box is split into word boxes and number boxes,
matched to a problem type, and solved.  The user plans an operator for it later (see section 5, TO DO).  The STANDALONE SOLVER is wired into the calculator rows since 2026-11-09: a Ready problem picked in Operators > Algebra word problems is placed in a row and = calls its compute() (see section 7).  The operator that takes PASTED text is still not built.

The solver's rule (from number_puzzle.py): a family answers ONLY when (1) its wording pattern matches, (2) EVERY number in the problem was given a role by the pattern, and (3) the answer passes a
sanity check.  Anything else returns None (a "decline"), so the trained matcher can take over.  A wrong role must never become a wrong answer: a decline is always safe, a wrong number is the failure.

-----------------------------------------------------------------------------------------
  - The user pastes a "job" written by Grok after it reviewed the last commit.  It says what is right, what is still wrong (with the exact sentence and the wrong number it returned) and what the next three families (or fixes) are.
  - "One commit, the same checks, then push."  The same checks, every time:
      * all tests pass (python -m unittest test_word_solver test_number_puzzle);
      * the 1,000 generated problems: claims go up by exactly the new template's problems, WRONG stays 0, and list every new claim (ids and answers) in word_solver_results.txt;
      * every decline the job lists is covered by a test (a test per sentence, with the right answer named in a comment);
      * "stay" cases: the sentences the job says must still answer are asserted unchanged;
      * exact fractions in the values and in the readings (31/5, never 6.2);
      * spelled numbers (two, three, twice, half ...) decline unless they are a count the equation uses; each / apiece / per right after a TOTAL price declines;
        "such", "of the year", "for part of", "of the time" decline when they change the equation;
      * no control characters in the .py files (a test reads every .py file) and no module-level name defined twice (a test checks word_solver.py);
      * the no-raise guard: no family may raise on any input, cut up or not;
      * write ONE FRESH SET after all the new families are finished, run it ONCE, do NOT tune on it.  If it finds a wrong answer, fix it, say so in the notes, call that set a "development set" in its test and write a new fresh set;
      * hand-written problems the solver now answers must be added to HAND_ANSWERS with the hand-calculated answer (the test fails otherwise and tells you which sentence);
      * add a "Batch N" section to word_solver_results.txt, then commit and push ONCE, with the trailer  "Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>"  (use the one in the current system reminder).
  - Report to the user in plain words: what changed, the claim count, hand-written count, the fresh set result, anything you decided that the job did not say.  Say it when a required decline had to become an answer and you changed an
    old test's expectation (those changes are always written in the test and in the results file).
  - A new family: copy the generator wording (algebra_problem_generator.txt) AND the user's example wording; support both.  A decline is always the safe answer.

TECHNICAL LESSONS (each one cost a bug):
  - NEVER type "\b" (or any backslash escape) inside a NON-raw Python string when writing code through a script: "\b" becomes a backspace character.  Use raw strings (r"...") and the Write / Edit tools; the control-character test
    catches it.  When a heredoc fails with quoting trouble, write the script with the Write tool instead.
  - Module-level names in word_solver.py are shared by all families.  Reusing a name (_UP, _DOWN, _TIME_UNIT were each reused once) silently broke an older family (22 percent problems went to 0 claims).  Give every new
    constant a family-specific prefix; the duplicate-name test now fails if a name is defined twice.
  - clean() lowercases and turns the word "percent" into "%", "−" into "-", and removes thousands commas: patterns must be written for the cleaned text.  digit_numbers(problem) returns (value, is_money, start, end) and does NOT
    include a minus sign.
  - Families run in FAMILIES order and solve() declines if two families answer differently, so a new family that overlaps an old one can break the old one's claims: always compare the generated claim counts per family.
  - "Whack-a-mole" lists of bad words do not work (a drain "covered" was missed after "sealed, capped, plugged"): prefer a general rule (a contrast word declines; nothing else may be said about X).
  - Run scripts from algebra_matcher/ with  PYTHONPATH=.  when they live elsewhere.
